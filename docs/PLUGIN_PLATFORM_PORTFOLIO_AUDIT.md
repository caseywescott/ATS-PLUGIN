# Portfolio Audit: Inputs to the Reusable Plugin Platform

Audit date: 2026-08-31. Source inspection, not runtime qualification.  
Companion to the [platform specification](PLUGIN_PLATFORM_STRATEGY_SPEC.md).

## 1. Scope and method

The eight supplied folders plus ATS contain eleven identified plugin products
across nine codebases. CF's two products share a kit; Mirage has an instrument
and an FX target. Applications, offline tools, tests and prototype/reference
code are not counted as additional plugin products.

The [inventory](PLUGIN_PLATFORM_DEPENDENCY_INVENTORY.md) is generated by
[audit_juce_portfolio.py](../scripts/audit_juce_portfolio.py). Its
[JSON](PLUGIN_PLATFORM_DEPENDENCY_INVENTORY.json) records every matched symbol's
source locations, primary module owner, configured scopes, read errors, Git HEAD
and a hash of the source/build files read. It includes uncommitted working files.
No sibling source files were edited or their plugin test suites executed.

These are lexical counts, not migration percentages or unique runtime dependencies.
Nested names such as `Colour::fromRGB` count separately. MIDI includes its legacy
and replacement trees. Comments/inactive branches can match; unqualified aliases,
inheritance and generated/transitive code can be missed. Tests/vendor libraries
are excluded from counts and need separate production/build/test dependency review.
Zero symbols in ATS/CF does not certify a JUCE-free shipped binary.

## 2. Findings by codebase

### CF: the best existing platform seed, with important limits

Sources: [build targets](</Volumes/Extreme SSD/COMPRESSED_FEEDBACK/CompressedFeedbackVST/CMakeLists.txt>),
[PluginModel](</Volumes/Extreme SSD/COMPRESSED_FEEDBACK/CompressedFeedbackVST/kit/clap/PluginModel.h>),
[buffer helper](</Volumes/Extreme SSD/COMPRESSED_FEEDBACK/CompressedFeedbackVST/kit/core/AudioBufferView.h>),
[MIDI helper](</Volumes/Extreme SSD/COMPRESSED_FEEDBACK/CompressedFeedbackVST/kit/core/MidiBuffer.h>),
[state codec](</Volumes/Extreme SSD/COMPRESSED_FEEDBACK/CompressedFeedbackVST/kit/core/State.cpp>),
[oversampler](</Volumes/Extreme SSD/COMPRESSED_FEEDBACK/CompressedFeedbackVST/kit/core/Oversampling.h>).

Observed:

- Shared `KitCore`, `KitDsp`, `KitClap`, optional `KitUi`, with separate product
  engines/parameters/presets/layouts. This already proves a two-product structure.
- CLAP modules plus optional clap-wrapper VST3, AUv2 and standalone targets.
  UI and wrappers default OFF: a default core/CLAP build is not a complete UI release.
- Host smoke registration expects 93 CF parameters and 129 CFSynth parameters;
  these are current source/test expectations, not independently captured release ABI.
- CompressedFeedback and CFSynth have separate CLAP/bundle identities and AU
  type/subtype choices. Preserve them separately rather than deriving identity
  only from an instrument/effect boolean.
- Parameter metadata includes type/range/skew/symmetric-skew/choices; CLAP IDs
  derive from strings. Product model lives under `kit/clap` but is mostly neutral.

Limits that matter for reuse:

1. `PluginModel` has simple channel counts, a sidechain boolean, limited transport
   fields and no full event-port/output/payload contract. Default action hooks can
   be no-ops. This is insufficient for Mirage and MIDI-only/network products.
2. `MidiMessage` stores three bytes; `MidiBuffer::addEvent` inserts into a vector
   without a declared fixed capacity. It is neither arbitrary SysEx transport nor
   a proven bounded RT event store.
3. The non-owning `AudioBufferT` constructor still creates a vector of channel
   pointers. `ClapPlugin.cpp` constructs these wrappers in its processing path
   (around lines 718–729). Split allocation-free views from owned storage before
   extracting this as the platform's realtime API.
4. `State.cpp` has a small hand-written parameter JSON/XML reader; it applies
   defaults and values through callbacks during parsing. It is not an all-or-nothing
   document transaction and does not cover Mirage/Heart/MIDI/ATS state structures.
5. `Oversampling.h` explicitly does not reproduce JUCE's equiripple coefficients;
   it implements a 2x windowed-sinc FIR. Other products require different profiles.
6. FFT scratch and oversampler storage need explicit lifecycle/thread ownership
   and allocation tests before broad reuse.

Reusable: parameter schema/registry, host-neutral seams, CLAP shell, widgets,
test patterns and selected DSP primitives. Product-owned: nonlinear feedback
algorithms, harmonic processing, CF synth behavior and specialized visual effects.

Historical evidence: [CF interaction post-mortem](</Volumes/Extreme SSD/COMPRESSED_FEEDBACK/CompressedFeedbackVST/CF_SYNTH_UI_INTERACTION_POSTMORTEM.md>)
describes rendered-but-noninteractive controls, coordinate interpretation and
popup/parent ownership failures. The [shared playbook](</Volumes/Extreme SSD/COMPRESSED_FEEDBACK/CompressedFeedbackVST/JUCE_REMOVAL_COMMON_ISSUES_AND_REUSABLE_PLAYBOOK.md>)
is useful evidence, not a directive to write another full migration spec per product.
Turn its repeated checks into shared conformance tests and manifest fields.

### Mirage: preserve the pure engine; replace the application layer

Sources: [instrument processor](</Volumes/Extreme SSD/EnsoniqMirage/mir8/plugins/mir8/PluginProcessor.cpp>),
[instrument interface](</Volumes/Extreme SSD/EnsoniqMirage/mir8/plugins/mir8/PluginProcessor.h>),
[FX processor](</Volumes/Extreme SSD/EnsoniqMirage/mir8/plugins/mir8-fx/PluginProcessor.cpp>),
[instrument target](</Volumes/Extreme SSD/EnsoniqMirage/mir8/plugins/mir8/CMakeLists.txt>),
[FX target](</Volumes/Extreme SSD/EnsoniqMirage/mir8/plugins/mir8-fx/CMakeLists.txt>).

Observed:

- Separate pure `engine` and `formats` libraries: voice/memory/chip/filter behavior,
  capture, sequencer, wavesample editing and modern modes; disk/preset/calibration
  formats and offline tools. These do not need a new common synthesis architecture.
- Two independently identified products: MIR-8 (`Cwsc`/`Mr8i`,
  `com.caseywescott.mir8`) and MIR-8 FX (`Cwsc`/`Mr8f`,
  `com.caseywescott.mir8fx`). CMake declares VST3/standalone plus AU on Apple.
- MIR-8 accepts and produces MIDI; FX declares input but no output. The
  instrument handles local keyboard, thru, program selection, CC, pitch bend,
  channel and poly pressure. Do not reduce its event model to note-on/off.
- Instrument `processBlock` captures input before clearing the shared audio
  buffer; pending capture commands and completion cross audio/UI boundaries.
- Audio import uses `AudioFormatManager/Reader`. UI provides waveform/envelope/
  keymap/memory/filter/LCD controls, file workflows, keyboard and undo.
- State around lines 1286–1390 stores APVTS plus OsPrograms, Wavesamples and
  Sequences; captured memory bytes use `MemoryBlock::toBase64Encoding`.
  Some state work currently takes `getCallbackLock()`; the new platform must
  provide coherent snapshots rather than mechanically preserving blocking design.
- FX has a smaller parameter state and generic-editor route; MIDI declaration
  alone does not prove its DSP consumes every MIDI message.

Needed: ASSETS/capture publication, complete MIDI transport/output, legacy-state
extensions, edit/undo service, generic and custom UI primitives, native file/host
services. SysEx-capable transport is a platform requirement to qualify; this audit
does not establish Mirage SysEx patch-loading support. Do not replace Mirage
voice allocation with Heart or CF's policy.

### GraphicEQ / Avedis E12G: compact UI, nontrivial DSP dependency

Sources: [processor](</Volumes/Extreme SSD/GraphicEQ/source/PluginProcessor.cpp>),
[transformer DSP](</Volumes/Extreme SSD/GraphicEQ/source/dsp/OutputTransformer.cpp>),
[build](</Volumes/Extreme SSD/GraphicEQ/CMakeLists.txt>).

Observed: mono/stereo effect, APVTS parameters, custom EQ/nonlinear stages, meters,
XML state and AU/VST3/standalone targets. Manufacturer/code are `Greq`/`Ae12`.
`OutputTransformer::prepare` creates JUCE 2x and 4x polyphase-IIR oversamplers.
HQ/transformer/bypass changes trigger latency updates; the processor keeps a
latency-aligned dry ring. Buffer operations and the transformer API also use JUCE.

Needed: PARAM/STATE/HOST/UI plus DSP oversampling and RT views/meters. Preserve
oversampling response and dry/wet timing; CF's FIR is not a drop-in equivalent.
This is a good smaller FX migration, but not a trivial dependency substitution.

### HeartSynth: voice framework + worker + genuine 3D UI

Sources: [voice](</Volumes/Extreme SSD/HeartSynth/Source/DSP/HeartVoice.h>),
[voice allocator](</Volumes/Extreme SSD/HeartSynth/Source/DSP/HeartSynthesiser.cpp>),
[table worker](</Volumes/Extreme SSD/HeartSynth/Source/DSP/TableBuildWorker.cpp>),
[table bank](</Volumes/Extreme SSD/HeartSynth/Source/DSP/TableBank.h>),
[renderer](</Volumes/Extreme SSD/HeartSynth/Source/UI/HeartRenderer.cpp>),
[processor state](</Volumes/Extreme SSD/HeartSynth/Source/PluginProcessor.cpp:409>).

Observed: HeartVoice/HeartSound inherit JUCE voice/sound classes; HeartSynthesiser
overrides free/steal selection. Voices use ADSR and smoothing. TableBuildWorker
inherits JUCE Thread; table construction takes JUCE FFT. UI uses OpenGL context,
shader program, mesh/camera/interaction plus a 2D fallback, scopes, modulation
controls and a keyboard collector. `HEARTSYNTH_STATE` wraps parameters and editor
camera/context/preset properties.

Needed: optional VOICE policies, DSP parity, JOBS cancellation/publication,
MIDI keyboard scheduling, state extensions and GPU surface lifecycle. Visage's
2D primitives alone do not establish 3D parity. Preserve the fallback's behavior
and do not treat it as permission to discard the main renderer.

### HydroSynth: DSP-to-APVTS coupling is the main architectural seam

Sources: [HydroModel interface](</Volumes/Extreme SSD/HydroSynth/Source/DSP/HydroModel.h>),
[parameter application](</Volumes/Extreme SSD/HydroSynth/Source/DSP/HydroModel.cpp>),
[voice](</Volumes/Extreme SSD/HydroSynth/Source/DSP/HydroVoice.h>),
[processor](</Volumes/Extreme SSD/HydroSynth/Source/PluginProcessor.cpp>).

Observed: `HydroModel::applyParameters` and value readers accept APVTS directly.
HydroVoice is a custom voice implementation with ADSR, not a JUCE SynthesiserVoice.
HydroModel/voice/modulator/noise generator use explicitly seeded JUCE Random.
The processor has a bounded local-MIDI array. State has HYDROSYNTH_STATE plus
a separate PROCESSOR_STATE carrying preset and editor context. UI shares many
widget/preset/modulation patterns with Heart but uses its own visualization.

Needed: generated typed parameter snapshot replaces APVTS in the engine; compatible
ADSR/RNG semantics; MIDI/RT publication; PARAM/STATE/OS/UI services. Keep the
custom Hydro voice/ladder implementation. A parameter named oversampling does
not prove this product uses JUCE's oversampler.

### MIDI Collab: second platform seed, not just another audio effect

Sources: [legacy/replacement build switch](</Volumes/Extreme SSD/MIDI_COLLAB_MINIMAL/juce_plugin_server/plugin/CMakeLists.txt:105>),
[replacement targets](</Volumes/Extreme SSD/MIDI_COLLAB_MINIMAL/juce_plugin_server/plugin/Source/replace_juce/CMakeLists.txt>),
[backend ADR](</Volumes/Extreme SSD/MIDI_COLLAB_MINIMAL/docs/adr/ADR-REMOVE-JUCE-005-ui-and-plugin-wrapper-backend.md>),
[network session](</Volumes/Extreme SSD/MIDI_COLLAB_MINIMAL/juce_plugin_server/plugin/Source/replace_juce/network/session/network_session.h>),
[network facade](</Volumes/Extreme SSD/MIDI_COLLAB_MINIMAL/juce_plugin_server/plugin/Source/replace_juce/host/network_client_facade.h>),
[standalone MIDI](</Volumes/Extreme SSD/MIDI_COLLAB_MINIMAL/juce_plugin_server/plugin/Source/replace_juce/host/standalone/midi_only_standalone.mm:350>).

Observed:

- Large legacy JUCE surface includes piano roll, CC/event lists, selection,
  transforms, clipboard, MIDI files, playhead/clock compensation, networking,
  account/room UI, threading and properties/settings. A synth-only platform
  contract cannot cover this MIDI-only application/plugin.
- `Source/replace_juce` already separates model/edit history, realtime MIDI,
  SMF codecs, protocol/session/transports, state codecs, host seams and Visage UI.
  The top-level legacy build option defaults ON, so replacement source presence
  does not mean all default targets are JUCE-free.
- Its ADR records CLAP-first + wrappers + Visage and initial pins CLAP 1.2.10,
  clap-wrapper v0.15.1, Visage `8280370...`. Current CMake accepts external roots
  and built libraries; an ADR pin is not proof a local build used that revision.
- Actual native SecureTransport and SChannel implementation files exist.
  The facade selects a native provider on macOS/Windows, while test seams also
  support passthrough. Do not call the whole network stack a stub.
- `NetworkSession::Options::tlsVerifyPeer` defaults false for historical
  self-signed behavior. Secure platform defaults and compatibility with that
  server model need an explicit decision, not silent inheritance.
- The realtime MidiEvent struct is three bytes plus timestamp; standalone code
  explicitly ignores SysEx payloads. Future common MIDI transport must declare
  these limits or supply tested payload handling.
- Native file dialog code exists for macOS and Windows; the Windows code is
  in a file named `native_file_dialog_stub.cpp`. Filenames are not capability proof.

Reusable: bounded queue/scheduler patterns, edit/history primitives, SMF/state
codecs, platform interfaces, native transport/dialog implementation candidates,
host/Visage tests. Product-owned: collaboration message schema, rooms/auth,
network reconciliation, musical transformations and piano-roll product behavior.

Needed before extraction: prove production callback paths, trust/reconnect/clock
behavior, MIDI output/dialect limits, real per-OS UI/device operation, and state
compatibility. Historical ADR stop points and license conclusions are not current
instructions or evidence of present build status.

### PunchGate: sidechain and dynamic latency must be shared host capabilities

Sources: [processor](</Volumes/Extreme SSD/PunchGate/plugin/Source/PluginProcessor.cpp>),
[processor interface](</Volumes/Extreme SSD/PunchGate/plugin/Source/PluginProcessor.h>).

Observed: optional mono sidechain bus; custom detector/filter/gate/lookahead/linking
DSP; APVTS and XML presets; JUCE 2x polyphase-IIR oversampling. Lookahead and
oversampling determine latency. An AsyncUpdater coalesces notification to
`setLatencySamples`; UI includes channel strips, advanced controls and meters.

Needed: explicit bus views, detector routing, oversampling profile, preparation
and reset contracts, dry/wet/lookahead alignment, latency notification service,
state/preset bindings and common controls. Do not make per-product host adapters
reimplement this lifecycle behavior.

### SNDWARP: assets and live buffers cannot be reduced to parameters

Sources: [processor and loaders](</Volumes/Extreme SSD/SNDWARP/Source/PluginProcessor.cpp>),
[processor interface](</Volumes/Extreme SSD/SNDWARP/Source/PluginProcessor.h>).

Observed: own SndwarpEngine/SourceBuffer/WindowTable/BalanceProcessor; JUCE-facing
audio buffers, parameters, linear smoothers, file readers, AsyncUpdater and UI.
Source/custom-window loaders decode samples and build native tables; file source
is resampled to the current target rate. The engine also has live source/freeze
behavior. State stores file paths and factory preset selection, not automatically
an embedded self-contained sample archive. Shared pointers and path locking need
explicit ownership review during the port.

Needed: audio codec/resampling service, immutable table publication/reclamation,
capture/live-buffer lifecycle, file chooser/drag-drop/errors, missing-file recovery,
smoothing and state migration. Preserve custom-window normalization and source
sample-rate behavior as product DSP policy.

### ATS: reuse infrastructure, not its entire runtime

Sources: [HostAdapter](</Volumes/Extreme SSD/ATS-PLUGIN/src/host/HostAdapter.h>),
[parameters](</Volumes/Extreme SSD/ATS-PLUGIN/src/core/ParameterRegistry.h>),
[jobs](</Volumes/Extreme SSD/ATS-PLUGIN/src/engine/JobCoordinator.h>),
[publication](</Volumes/Extreme SSD/ATS-PLUGIN/src/engine/SnapshotPublisher.h>),
[file service](</Volumes/Extreme SSD/ATS-PLUGIN/src/platform/FileService.h>),
[native UI](</Volumes/Extreme SSD/ATS-PLUGIN/src/ui/VisageNativeMac.mm>),
[build gate](</Volumes/Extreme SSD/ATS-PLUGIN/CMakeLists.txt:497>),
[third-party notes](</Volumes/Extreme SSD/ATS-PLUGIN/THIRD_PARTY.md>).

Observed: neutral source, parameter/state infrastructure, typed UI actions,
workers and snapshots, native VST3/AUv2/standalone and Visage editor integration.
HostAdapter combines many ATS-specific analysis/edit/render responsibilities;
other model/playback services have overlapping roles. Current native editor code
has a production shell, so older documents describing only a probe are not a
reliable statement of current source. The native-editor build is Apple-only.

Reusable: generation/cancellation, publication, files, command/result contracts,
host and editor test patterns, selected geometry/cache abstractions. Keep ATS
spectral model, algorithms, historical binary-state interpretation and detailed
editor pages product-owned. Avoid copying large visualization data every timer tick.
Qatsh/ATSA and libsndfile remain external/provenance concerns even with JUCE gone.

## 3. Cross-portfolio conclusions

1. **There is already enough evidence to extract a framework.** CF has two real
   consumers; MIDI supplies the hardest non-audio requirements. A hypothetical
   second ATS plugin is no longer needed to justify shared infrastructure.
2. **The core must be smaller than the union of features.** Optional assets,
   voices, networking, timeline editing and GPU modules cover the portfolio
   without forcing an EQ to depend on a collaboration client or 3D renderer.
3. **Schemas and compatibility fixtures replace repeated migration prose.**
   Identity, parameters, state migrations, capability declarations and product
   fixtures remain per-product. Generic mechanisms/tests are written once.
4. **Sound and saved sessions are the expensive seams.** IDs, envelopes, random
   sequences, oversampling and resource encodings need behavioral contracts.
5. **Rendered UI is not working UI.** CF's history makes real dispatch, focus,
   popups and embedding tests mandatory shared infrastructure.
6. **Source availability is not qualification.** Every reuse candidate must pass
   its module contract on the selected OS/format/host matrix. No runtime or
   release pass has been inferred from this audit.

Implementation sequencing, full module requirements and release gates are in
the [master specification](PLUGIN_PLATFORM_STRATEGY_SPEC.md).
